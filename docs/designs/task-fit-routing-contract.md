# 任务适配路由：第一阶段算法与接口草案

状态：第 1–5 节已实现；第 6 节语义质量评价尚未实现。依据[已确认目标](task-fit-routing.md)细化；示例数字用于说明契约，不是实测推荐参数。

## 1. 将三个概念分开

- 验收定义：任务产出必须满足什么，由宿主提供，并通过 `acceptance.version` 隔离质量证据。
- 质量偏好：希望达到的通过率，以及超过目标之后继续提升可靠性的价值。
- 资源准入：预算、单次费用上限、调用次数和截止时间，决定能不能发起调用，不决定质量值多少钱。

第一阶段继续使用固定画像 Q 作为验收通过倾向。精度、完整性等要求应进入版本化验收定义；不从名次或模型自报置信度推导这些维度的分数。任务难度暂通过宿主提供的证据与验收定义表达，不声称已有自动难度预测器。

## 2. 任务级接口

建议在 SubmissionSpec、执行 TaskSpec 和有效计划中加入 `selection`，原始提交和生效值分别保留。下例明确表达一组宿主偏好：

```json
{
  "selection": {
    "version": "host-task-fit-v1",
    "min_quality": 0.75,
    "target_quality": 0.90,
    "above_target_factor": 0.10,
    "cost_reference": 10000,
    "latency_reference_ms": 5000,
    "min_upgrade_gain": 0.05
  }
}
```

约束：`0 <= min_quality <= target_quality <= 1`；`above_target_factor` 为有限的 0..1；`min_upgrade_gain` 为有限的 (0,1]；费用参考为 1..i64::MAX 的整数 microcredits；延迟参考为 1..86,400,000 毫秒；version 非空且最多 256 UTF-8 字节。拒绝未知字段。

参数由宿主明确提供；不从预算推导默认成本参考。初版引入新提交契约版本并同步迁移仓库调用方，缺失参数拒绝并给出字段提示，避免静默替用户设置质量要求。旧持久化任务证据保留读取能力，不重放调用。规划模型不得更改 selection，宿主明确选择保持优先。

`min_quality` 为候选的预期质量下限，不是实际产物免检线；`target_quality` 为边际收益折减点，也不代替产出验收。对于 critic 节点，首版沿用固定角色画像及既有评分，不将生成任务的质量偏好直接套用为 critic 正确性门槛。规划器继续使用宿主池和全局先验。

## 3. 评分公式

对于通过全部硬约束且 Q 达到 min_quality 的生成候选：

```text
quality_value(Q) = min(Q, target_quality)
                 + above_target_factor * max(Q - target_quality, 0)

score = quality_weight * quality_value(Q)
      + capability_weight * preferred_capability_match
      + reliability_weight * reliability
      - cost_weight * estimated_call_cost / cost_reference
      - latency_weight * estimated_latency_ms / latency_reference_ms
      - uncertainty_weight * uncertainty
```

质量、能力、可靠性等权重继续来自任务固定画像。成本和延迟不使用预算或剩余截止时间作偏好归一化；实时预算和截止时间仍必须执行。评分不截断成本惩罚，避免昂贵候选超过参考值后价格差别消失。

初版选择的是单次调用价值，不能称为协作总成本最优。一次便宜调用后可能升级的额外成本将在有条件失败数据后建模；当前仅明确记录已花费用、剩余额度和下一次预估费用。

### 榜单的位置

外部榜单不能作为证明额外质量收益的依据。此草案将其从直接加分改为主评分完全相等时的辅助排序：主评分降序 → 已匹配榜单贡献降序 → 预估费用升序 → 模型 ID 升序。不使用近似相等比较，保证排序关系稳定。缺失榜单仍保留未知状态，不改变 Q。

这是对早期榜单直接加分行为的明确调整；配置指南、快照版本、复算逻辑和测试已同步。旧快照依其记录的算法版本复算，不用新公式重新解释旧决策。

## 4. 计算例子

只比较质量与成本，其他项相同，质量权重为 1、成本权重为 0.1，成本参考为 10000，目标为 0.90，目标以上系数为 0.10：

| 场景 | 经济候选 Q / 费用 / 得分 | 强候选 Q / 费用 / 得分 | 首选 |
| --- | --- | --- | --- |
| 简单任务 | 0.90 / 1000 / 0.890 | 0.95 / 4000 / 0.865 | 经济候选 |
| 困难任务 | 0.76 / 1000 / 0.750 | 0.95 / 4000 / 0.865 | 强候选 |

以上是合成算例。保持其他输入和候选集合不变，提高预算不会改变这两组结果。更改验收标准后必须使用对应版本的 Q，不能把同一质量估计随意标记为简单或困难。

## 5. 动态升级

初版复用 cascade 的生成、确定性检查和反馈上下文：

1. 保存本轮产物和评价；通过则停止。
2. 仅 Revise 结论允许升级。HumanRequired、MissingEvidence、Unacceptable 继续保持各自停止语义。
3. 升级候选不能是本任务已尝试的生成候选，且必须满足 `Q_next >= Q_previous + min_upgrade_gain` 和所有原有约束。门槛大于 1 时直接视为无升级候选，不截成 1 制造虚假提升。
4. 在满足升级门槛的候选中按相同价值公式选择；先前产物和评价缺陷进入下一轮上下文，但不修改任务内固定 Q。
5. 无候选时返回 human_required，原因区分 no_quality_improvement、budget、constraints；保留最新产物。首次生成之前无候选仍返回 routing 错误。调用/轮次/截止时间耗尽分别保留既有终止语义。

此阶段只能根据任务级 Q 证明预期改善，路由证据明确标为 task_profile；缺陷用于后续生成，不宣称已经按缺陷类别匹配模型。若所有候选 Q 一致，则不能称换模型为升级。

## 6. 语义质量评价的下一步接口边界

确定性检查只能发现已编码的格式与内容要求，不能充分覆盖语义质量。完整目标还需要在 cascade 中可选执行独立 critic，再决定升级。

该扩展复用现有 Evaluation 与 CriticVerdict：确定性检查通过后运行无工具权限的 critic，保存其原始结论和调用归因；Revise 触发模型升级，Pass 允许完成，其他结论保持停止语义。不同评审模型约束仍生效；critic 结论不自动生成业务反馈。

评审须共享调用额度、预算与截止时间；协议非法、取消、超时或调用失败不得被转成 Pass。评审中断时保留候选及确定性证据并完成账务清理。首版先复用模型 critic，不新增未定义计费方式的宿主运行中回调。实际业务反馈继续使用终态接口。

这部分单独实施，完成前只能宣称支持确定性检查驱动的升级，不能宣称全面识别质量不佳。

## 7. 实施顺序与交付检查

1. 契约：`src/contracts/planning.rs`、`src/contracts.rs`、配置校验与仓库 Rust/Python 调用方同步；测试拒绝非法字段、范围及规划覆盖。
2. 纯路由：新增 `src/router/selection.rs` 管理价值函数与比较键；`profiles.rs` 固定参数和算法版本，`router.rs` 复用过滤并记录评分分解。用第 4 节数值做精确行为测试，覆盖预算不变性和榜单不能推翻主评分。
3. 升级：`src/engine/execution.rs` 使用严格改善门槛并保留无候选产物；测试一轮通过、升级成功、无改善候选、预算拒绝、取消/超时与未知费用。
4. 独立 critic：扩展策略契约和有效计划节点，复用已有评审调用及分层存储；测试双协议、本轮升级归因、评审失败不能完成、不同模型约束与调用额度耗尽。
5. 持久化：参数、算法版本与有效计划原子保存；每次升级原因与路由输入可查。若无需表结构变更则保持 SQLite schema 2；如需变更，遵守拒绝旧 schema、备份重建而不自动清库的规则。
6. 文档及技术图：新旧算法行为明确分界，同步 JSON 示例、README、榜单指南、架构及反馈图；按 archify 分别检查结构、浏览器与视觉。
7. 验证：先新增失败测试，再实现；执行仓库 Rust、Clippy、fmt、原生重建、Python、Ruff 检查。离线行为验证与真实业务收益评测分开报告。

不在本阶段加入自动难度学习、随机探索、强弱配额或未经校准的协作总成本预测。
