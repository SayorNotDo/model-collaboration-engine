# 首轮真实模型对比评测方案

方案关系图见[策略对比评测](../diagrams/evaluation-plan.html)；方案已于 2026-09-16 确认；脚本实现与模拟验收见[实施记录](live-evaluation-implementation.md)，限定范围真实验证见[联调结果](live-evaluation-results.md)。

## 目标与现状

验证真实兼容服务能否完成模型调用、验收和费用记录，并观察同一任务集上 single 与 cascade 的质量、成本和延迟差异。首轮属于小规模试验，不据此宣称统计显著收益。

现有 Engine 已提供执行、评价、反馈和指标接口；`examples/compare_metrics.py` 只比较导出的指标，没有负责运行任务。此次复用这些接口，不修改执行内核、路由算法或 SQLite schema。当前仓库配置为占位服务，真实运行所需配置路径、候选模型和总费用上限由宿主提供；密钥通过环境变量读取。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| 独立 Python 评测脚本（建议） | 复用公共 API，任务集、配置和输出可保存，适合首轮对比 |
| 手动运行现有示例并导出指标 | 改动少，但难以保证逐任务配对、相同预算和完整失败记录 |
| 引擎内置评测调度与持久化任务队列 | 可扩展，但增加运行时和存储职责，超出首轮验证需要 |

## 首轮范围

- 提供 12 个固定信息抽取任务，输入全部为合成文本；参考答案与版本化验收规则随任务集保存。
- 对比 single 与 cascade，两组使用相同候选池、权重、输入、验收版本、单任务预算、输出上限及截止时间长度，仅改变 strategy。明确任务类型并关闭规划，避免混入规划开销。
- 每组使用全新的独立数据库，串行运行；按任务交替两组先后顺序，记录实际顺序。此安排降低顺序偏差，不保证消除服务波动。
- 首轮只调用模型，不声明宿主工具。工具协议及自动规划的真实验证另设实验，结果不混入本轮策略对比。
- 先用一个样例对配置做最小联调；联调费用计入总准入额度，联调记录单独保存，不计入对比组。

## 输入、输出与职责

已新增 `examples/evaluate.py` 和合成任务集；入口参数包括配置路径、任务集路径、输出目录及整数 microcredits 总准入额度。复用现有指标比较函数，避免新增一套费用计算口径。

配置中的模型 ID、版本、端点、价格版本必须显式提供；拒绝占位模型。开始前检查声明的凭证环境变量是否存在，仅报告变量名。不把密钥值保存到输出或错误摘要。

输出目录必须是新目录，存在时拒绝覆盖。保存本轮配置与任务集摘要、执行顺序、逐任务结果/错误、候选与验收证据、单调时钟测量的任务耗时、各组 metrics 和对比报告。文件中的配置仅含环境变量名，不包含其值。

数据库保存 Engine 证据，脚本只管理本轮顺序与文件输出。中断后保留已完成输出和数据库；首版拒绝自动续跑，避免重复调用或污染样本。

## 验收与反馈

确定性业务验收要求候选能解析为 JSON，键集合与参考答案一致，字段类型和值逐项相同。参考答案不包含在模型提示中。引擎自身的 nonempty/json_object 检查与业务正确性分别记录。

所有模型调用完成后，再对已终态任务中保存的最终候选提交 business_acceptance 反馈，使本轮反馈不影响后续配对任务的路由。已有候选的失败任务可按保存证据评价；没有候选的任务记录为无产物，不伪造反馈或 critic 正确性结论。

报告分别显示执行状态、全任务正确产出数/计划任务数、已评价产物通过率、无产物数、未执行数、已知费用、未知费用尝试、调用次数及端到端耗时。调用平均延迟继续来自 metrics；两种延迟分别标注。保留验收版本分组，不将未执行或未知费用记为零成本成功。

## 预算、失败与取消

首轮按最坏情况分配额度：联调和两组全部任务的预算之和不得超过宿主给定总准入额度，超出时在任何派发前拒绝。这是准入控制；供应商实际 usage 仍可能超出预留，不承诺账单硬上限。

已知费用超额或存在费用未知的调用时停止派发后续任务，保留证据并报告原因。初始配置、凭证、数据库或输出写入失败同样停止；普通任务验收未通过则记录后继续。脚本不额外重试模型，策略内尝试仍由 Engine 的限制控制。

使用 Engine 异步上下文完成收尾。取消后等待运行及回调清理；如无法导出最终指标，明确标记导出失败并保留数据库，不将本轮报告为完整结束。

## 验证与完成条件

使用本地模拟服务验证：两个策略运行同一任务集、反馈推迟到运行完成后、错误/无产物分别记载、超出准入额度在派发前拒绝、未知费用停止后续派发、输出目录不被覆盖，以及中断保留证据。对应测试放在独立 Python 测试文件中。

真实运行前需确定服务配置、模型池和预算。完成标准是联调有真实请求证据，每个计划样例具有结果或明确的未执行原因，两组费用和评价可追溯到数据库，报告区分模拟验证与真实运行。凭证未提供时仅能完成脚本与模拟验证，不报告真实联调成功。

实现通过独立示例复用公共接口；真实运行仍需实际配置与明确额度。

## 基线检查发现

以下为修复前的历史记录。2026-09-16 已确认短窗口可能在派发前耗尽，导致顺序 Fake 的 Block 被后续生成调用消费；现已使用通知与时钟边界分别验证派发后保留未知预留、未派发结算零费用及全局截止不回退。`cargo test --all-features --locked` 全量 67 项通过，该历史基线问题已关闭。

当前 Windows 工作区运行 `cargo test --all-features --locked` 时，`planning_stage_timeout_can_fall_back_but_global_deadline_cannot` 在 planning.rs:288 返回 deadline，规划套件为 13 通过、1 失败；单独运行该用例通过，随后再次运行 planning 套件仍同样失败。数据库 3 项、执行 20 项和反馈 8 项在首次运行中通过；后续路由套件和文档测试因前序失败未执行，Python 尚未重建或验证。

真实评测前先定位此条件敏感的基线失败。重点核对 50ms 规划窗口、派发前账务耗时与 Fake 按调用顺序消费 Block/Reply 的关系；这是待验证假设，不是已确认的产品缺陷。修正需保持阶段超时可回退、全局超时不可回退的既定语义，并分别验证实际派发与未派发的费用证据。
